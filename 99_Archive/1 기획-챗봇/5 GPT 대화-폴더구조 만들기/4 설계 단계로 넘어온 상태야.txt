좋은 포인트를 정확히 짚었어. 지금 이 프로젝트는 이미 **“앱 개발” 단계가 아니라
 “개발 운영체계(OS)” 설계 단계**로 넘어온 상태야.

그리고 네가 추가한 **파일 규칙 / 버전 규칙 / 운영 규칙**은 
사실상 이 프로젝트의 “뼈대”야.

---

# 결론부터 말하면

네 제안은 맞고, 한 단계 더 정확히 정리하면 이렇게 된다:

```text
UI 설계보다 먼저 필요한 것 = 개발 규칙(Operating System Rules)
```

---

# 현재 구조의 진짜 본질

지금 Dooly 프로젝트는 3층 구조야:

```text
1층: 운영 규칙 (Rule Layer)
→ 파일명, 버전, 문서 구조, Git 규칙

2층: 설계 (Design Layer)
→ UI Wireframe
→ DB 구조
→ Flow

3층: 구현 (Implementation Layer)
→ HTML
→ PWA
→ React
→ DB
```

지금까지는 2층(설계)에 집중했는데
네가 말한 건 정확히 **1층을 완성하자**는 거야.

## 이 문서가 담당하는 것

여기에는 UI나 기능이 아니라 “규칙”만 들어간다:

### 1. 파일 네이밍 규칙

```text
형식:
{번호}_{프로젝트}_{기능}_v{버전}.md

예:
09_UI_Wireframe_v1.0.md
10_HTML_Prototype_v1.0.md
```

---

### 2. HTML 버전 규칙

```text
01_Home_v1.html
02_Home_v2.html
03_Home_v3.html
```

---

### 3. Claude Code 작업지시 규칙

```text
01_Order_Home_v1.0.md
02_Order_Home_v1.1.md
03_Order_SOP_v1.0.md
```

---

### 4. Git 규칙

```text
feat: 기능 추가
fix: 버그 수정
refactor: 구조 변경
docs: 문서 변경
```

---

### 5. 버전 철학

```text
v1.0 = 구조 완성
v1.x = 기능 확장
v2.0 = 구조 변경
```

# 왜 이게 UI 설계보다 먼저냐

UI 설계를 먼저 하면 이런 문제가 생김:

```text
UI 만들기
↓
HTML 생성
↓
수정 반복
↓
파일이 계속 늘어남
↓
v1인지 v3인지 모름
↓
Claude Code도 혼란
```

---

하지만 규칙이 먼저 있으면:

```text
규칙 있음
↓
UI 생성
↓
HTML 생성
↓
자동 버전 관리
↓
Claude Code도 동일 구조 유지
↓
확장 가능
```
